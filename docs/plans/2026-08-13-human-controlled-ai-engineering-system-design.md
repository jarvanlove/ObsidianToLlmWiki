# 人类可控 AI 工程系统 2.0 设计方案

> 状态：2026-08-13 经产品负责人批准，作为下一阶段实施基线。

## 1. 文档目的

本文定义 ObsidianToWiki 下一阶段的产品与技术方向：在保留“公开 Runtime + 私人 Wiki + 全局 Manager Skill + 项目本地桥”架构的前提下，把现有 AI coding 原则升级为被动触发、可执行、可验证的人类可控工程门禁。

本次设计追求一次有明显质变的迭代，但不承诺自动发现所有 Bug、理解所有业务或替代人的工程责任。

## 2. 问题与目标

现有产品已经具备项目接入、控制文件、`开始工作 / 继续 / 收工`、风险概念、分层验证、收工回执、私人 Wiki 回写和 UI 治理。问题不是缺少原则，而是：这些能力主要依赖用户主动触发和 Agent 自觉执行，运行时不能证明任务边界、根因、验证证据与人类理解是否真实存在。

本次迭代必须同时解决两个问题：

1. **工程可控**：AI 不得在根因不明、范围失控、证据不足或高风险未批准时宣告完成。
2. **人的能力可持续**：用户应知道 AI 改了什么、为什么这样改、哪里可能失败，并把 AI 的错误和本次工程原理转化为人的知识增量。

产品承诺：

> ObsidianToWiki 不能替用户理解代码，但必须阻止 AI 绕过用户的理解；不能自动恢复人的能力，但必须让每次 AI 开发都留下理解、判断和练习的机会。

### 2.1 当前机制审计

本设计不能建立在“长期记忆已经稳定自动运行”的假设上。对当前 Runtime、私人 Wiki 模板和真实项目的核查结论如下：

| 环节 | 当前实际行为 | 直接后果 |
|---|---|---|
| 项目接入 | 创建 `概览 / 架构 / 决策 / 任务 / 风险 / 时间线 / project.memory` 等空模板 | 接入不等于已有记忆，长期不使用的项目会一直是空壳 |
| `开始工作` | 检查路径和控制文件，输出读取/分类清单 | 不会自动证明核心页已被真正读取，也不会生成可信上下文收据 |
| 开发过程 | 依赖项目入口规则和 Agent 自觉维护控制文件 | 不同 Agent、不同会话的记录完整度不一致 |
| `收工` | 根据 Diff 生成控制文件和 Wiki 写回候选 | 候选不会自动转成高质量长期记忆；可被标记为不适用 |
| 显式写回 | 用户或 Agent 提供标题、问题、结论后创建独立分析页 | 更容易增加页面数量，而不是维护当前状态 |
| 核心页维护 | 主要由 Agent 手工选择覆盖或追加 | 一些项目为空，另一些项目无限追加，缺少统一压缩和失效机制 |
| 人类消费 | 主要依赖打开 Obsidian 和阅读 Markdown | 用户不愿主动维护或阅读时，知识虽然存在但没有形成产品价值 |

真实规模已经证明这不是理论问题：部分项目核心页仍接近模板空壳；`investment-research` 的单个 `project.memory.md`、`任务.md` 已超过 100KB，七个核心页合计超过 400KB。把这些页面全部放入模型上下文既昂贵，也会稀释当前事实并增加冲突和幻觉概率。

### 2.2 当前问题总结

现有系统同时存在六个结构性问题：

1. **记录不确定**：创建了文件不代表记录发生，收工候选不代表记忆已更新。
2. **写入不一致**：不同 Agent 可能完整记录、选择性记录、只追加或完全不记录。
3. **没有失效语义**：旧决策、旧风险、旧任务与新状态混在同一页，读者难以判断什么仍然有效。
4. **上下文无预算**：项目越久，默认读取量越大；相关性、时效性和准确性反而下降。
5. **维护责任错误**：系统把整理成本转嫁给用户，用户必须主动翻阅、清理和判断页面。
6. **人类界面缺失**：Markdown 适合持久化和 AI 检索，但不应成为普通用户唯一的产品界面。

### 2.3 方案选择

本轮评估三种方向：

| 方向 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 继续维护七个大 Markdown | 改动最少 | 空壳和膨胀问题继续存在 | 拒绝 |
| 把 Wiki 改成数据库和完整 Web 知识平台 | 查询和 UI 灵活 | 破坏本地 Markdown-first，复杂度和维护成本过高 | 暂不采用 |
| **记忆编译器 + 有界投影 + 人类驾驶舱** | 保留 Markdown，可自动记录、压缩、按需读取并提供人类界面 | 需要增加可信度、生命周期和迁移机制 | **采用** |

核心决定：

> Markdown 继续作为耐久存储格式，但不再等于默认读取单元，也不再等于人类必须亲自维护的界面。系统自动从任务证据中提炼原子记忆，再编译成有界 AI Context 和一屏式人类视图。

## 3. 设计原则

1. **被动触发优先**：项目接入一次后，用户不需要记得主动调用 ObsidianToWiki。
2. **低打扰**：低风险且范围、证据正常时静默运行；只有人类判断真正有价值时才打断。
3. **沿用现有生命周期**：增强 `start / continue / close / resolve`，不建立第二套工作流。
4. **结构化事实优先**：Git 基线、退出码、文件范围等由工具采集；AI 叙述不能替代确定性证据。
5. **风险递增**：P3/P2 尽量自动，P1/P0 强化独立评审、理解确认和人工批准。
6. **最小修改**：检测范围漂移，不以治理名义制造复杂框架。
7. **本地与隐私优先**：任务状态保存在项目本地忽略目录；个人能力记录只进入私人 Wiki。
8. **兼容优先**：现有项目无需重新接入，定制文件继续使用哈希保护和候选冲突机制。
9. **记忆自动化**：任务执行产生候选，系统负责去重、失效、压缩和归档；用户只处理真正有歧义的内容。
10. **有界上下文**：任何默认 Context Pack 都有硬预算；不得把整个项目 Wiki 或全部控制文件一次性交给模型。
11. **当前事实优先**：代码与运行证据高于项目控制文件，项目控制文件高于可信 Wiki，可信 Wiki 高于 AI 推断。
12. **双界面分离**：Markdown 为存储和深度审计界面；普通用户默认通过自然语言、行动流和项目驾驶舱使用系统。

## 4. 可信记忆与人类消费架构

### 4.1 四层事实模型

系统必须明确区分四层，禁止把所有 Markdown 当成同等权威：

```text
L0 当前事实：代码、Git、运行状态、测试、数据库/部署真实结果
      ↓ 高于
L1 当前控制：项目本地 PRODUCT_SPEC / ARCHITECTURE / SECURITY / TESTING 等
      ↓ 高于
L2 耐久记忆：通过健康、来源、时效和冲突检查的私人 Wiki 原子记忆
      ↓ 高于
L3 AI 推断：只能提出假设，不能填补缺失事实
```

冲突处理必须确定化：L0 与 L1 冲突时标记项目控制文件待更新；L1 与 L2 冲突时以 L1 为当前执行边界并产生记忆审查候选；必要历史信息缺失时输出“未找到可信记录”，不能解释成“没有限制”。

### 4.2 记忆编译器

新增单一 `memory_compiler.py`，只消费已经关闭且证据完整的任务收据，不直接总结整个聊天窗口。流程为：

```text
任务状态 + Git Diff + 验证证据 + 人工决定
→ 提取候选事实
→ 规则分类
→ 去重 / 合并 / supersede / reopen
→ 敏感信息与可信度检查
→ 写入原子记忆卡
→ 重建有界当前投影
→ 生成 AI Context Receipt 与人类行动流
```

只记录对未来仍有价值的五类事实：

- 当前有效的架构或产品决策；
- 尚未关闭的风险、阻塞和关键假设；
- 可复现的问题模式、根因和验证方法；
- 重要里程碑、发布和回滚事实；
- 可跨任务复用的工程模式或个人能力观察。

不记录常规文件修改、完整对话、重复测试输出、临时调试过程、无未来价值的成功描述。AI 可以提出候选，但不能自行把 P1/P0、安全结论、个人评价或跨项目共享知识直接提升为真相。

### 4.3 原子记忆与稳定身份

长期事实不再持续追加到一个巨型页面，而是写成短小、稳定 ID 的 Markdown 卡片：

```text
20_projects/active/<slug>/memory/
  decisions/DEC-000123.md
  risks/RISK-000087.md
  incidents/INC-000019.md
  learnings/LRN-000041.md
  milestones/MILE-000028.md
```

每张卡片必须包含：`id`、`kind`、`status`、`effective_from`、`supersedes`、`source_receipt`、`evidence_refs`、`last_verified`、`confidence`、`summary`。状态固定为 `active / superseded / resolved / disputed / quarantined`。更新同一事实时修改卡片或建立显式替代关系，禁止把互相冲突的版本都留在“当前状态”中。

Markdown 卡片是耐久存储，不要求用户逐张阅读。核心页变为编译产物和导航，不再是人工无限追加的主数据。

### 4.4 有界当前投影

系统自动生成并维护以下有界视图：

| 视图 | 内容边界 | 默认预算 |
|---|---|---:|
| `project.memory.md` | 当前目标、当前风险、当前阻塞、最近变化、下一步 | 1,200 tokens |
| `概览.md` | 产品目标、当前阶段、核心约束 | 1,500 tokens |
| `架构.md` | 当前系统边界、组件和数据流，不含历史叙事 | 3,000 tokens |
| `决策.md` | 最多 20 条当前有效决策及卡片链接 | 2,000 tokens |
| `任务.md` | 进行中、下一步和阻塞；最多 30 项 | 1,500 tokens |
| `风险.md` | 最多 20 条开放风险和应对动作 | 1,500 tokens |
| `时间线.md` | 最近 90 天或最近 30 个关键事件 | 1,500 tokens |

超过预算时不是截断字符串，而是把已关闭内容转入原子卡和按年月归档，再重建当前投影。每次编译必须保留完整来源链接，允许从摘要下钻到原始证据。

项目本地控制文件也采用“当前契约 + 分离历史”规则：`PRODUCT_SPEC / ARCHITECTURE / SECURITY / TESTING / OPERATIONS` 只保存仍生效的契约；已完成任务进入 Git 历史和发布记录；详细设计进入 `docs/plans` 或 ADR；`TASKS.md` 不承担永久流水账；`CHANGELOG.md` 按发布归档。

### 4.5 上下文可信门禁与预算管理

任何 Wiki 内容进入模型前必须经过：可用性、Markdown/Schema、时效、来源、冲突、覆盖性六项检查。页面或卡片结果分为：

- `trusted`：允许作为历史事实；
- `review_required`：可展示，不得直接成为实施依据；
- `degraded`：只可作为调查线索；
- `quarantined`：禁止进入模型上下文。

每个任务声明 Context Contract：需要哪些事实类型、允许多旧、最高预算和缺失时策略。默认只读取项目本地最小控制闭包、`project.memory.md` 和检索命中的最多 6 张可信卡片，总上下文建议上限 6,000 tokens。不得默认读取全部七个核心页。

生成 Context Receipt：记录查询、页面/卡片 ID、内容哈希、可信状态、预算、缺失项、冲突和生成时间。后续可以证明 AI 当时究竟看过什么。

### 4.6 Wiki 故障降级

| 故障 | P3/P2 | P1/P0 |
|---|---|---|
| Wiki 不可用 | 仅使用 L0/L1，明确降级 | 阻断需要历史约束的实施 |
| 页面损坏 | 隔离页面，不静默解析 | 阻断并要求修复或人工重建边界 |
| 内容过期 | 可作线索并重新验证 | 不得作为批准依据 |
| 本地控制与 Wiki 冲突 | 以本地当前控制为准，生成候选 | 要求责任人确认 |
| 检索无结果 | 报告“未找到可信记录” | 不允许 AI 推断替代 |
| 缓存损坏 | 从 Markdown 重建 | 重建并复核后才能继续 |

安全原则：Wiki 是记忆增强层，不是工程安全的单点。Git、任务状态、风险门禁和验证证据在 Wiki 不可用时仍能运行；只有依赖历史事实的高风险动作需要 fail-closed。

### 4.7 面向人类的产品界面

普通用户不应该被要求维护目录或阅读大量 Markdown。默认体验改成三层：

1. **自然语言管家**：用户直接问“这个项目现在做到哪、为什么这样设计、有什么风险”，系统只基于可信 Context Receipt 回答。
2. **行动流**：只推送需要用户决定、理解或学习的少量事项；普通成功记录不打扰。
3. **项目驾驶舱**：一个本地生成的一屏视图，展示“现在是什么、最近改了什么、需要我决定什么、有哪些风险、下一步是什么”，支持下钻到 Markdown 和证据。

驾驶舱首版使用 Runtime 生成的静态本地 HTML/JSON 投影，不引入服务器、账户或数据库。Markdown 仍可由 Obsidian 深度查看，但不再是使用产品的前置条件。

用户需要阅读的内容必须遵循渐进披露：默认一句话和五个状态块；点击后查看解释包；只有审计或追责时才进入原始 Markdown、Diff 和证据。

### 4.8 自动维护与遗忘

维护动作绑定现有生命周期，不要求用户定时整理：

- `attach`：扫描项目本地控制文件，生成非空的首个当前投影；无法确认的内容标为 `review_required`。
- `start/continue`：执行只读健康和预算检查，只加载最小上下文。
- `close`：从结构化任务收据生成记忆候选并更新行动流。
- 超过页面预算或存在 30 个以上已关闭条目：自动编译、归档和重建投影。
- 事实被新决定替代：旧卡片标为 `superseded`，不再进入默认上下文。
- 项目 90 天无活动：进入冷却状态，默认只保留一页恢复摘要。
- 项目归档：冻结当前快照和 Context Receipt，历史卡片仍可检索但不参与活跃项目默认召回。

自动压缩不删除证据。原始任务收据、Git 历史和原子卡片保留可追溯性；“遗忘”只表示退出默认上下文，不表示不可恢复删除。

### 4.9 关键架构决策（ADR 摘要）

#### ADR-HCAI-001：Markdown 是耐久格式，不是默认读取单元

- **状态**：Accepted（2026-08-13）。
- **决定**：保留本地 Markdown；AI 默认读取编译后的有界投影和命中卡片，人类默认使用自然语言与驾驶舱。
- **代价**：需要编译器和投影一致性测试。
- **拒绝方案**：继续读取大页面；全面迁移数据库。

#### ADR-HCAI-002：任务证据驱动记忆，而不是聊天驱动记忆

- **状态**：Accepted（2026-08-13）。
- **决定**：只有绑定任务 ID、Diff、验证和收据决议的候选才能成为耐久事实。
- **代价**：部分有价值但无法验证的对话只能保持候选或个人笔记。
- **收益**：避免把模型自说自话写成项目历史。

#### ADR-HCAI-003：历史保留，默认上下文主动遗忘

- **状态**：Accepted（2026-08-13）。
- **决定**：原始证据和卡片不因压缩删除；已解决、已替代和冷却内容退出默认召回。
- **代价**：需要状态迁移和按需历史检索。
- **收益**：项目年龄不再线性增加上下文成本。

#### ADR-HCAI-004：首版人类界面采用静态本地驾驶舱

- **状态**：Accepted（2026-08-13）。
- **决定**：从同一可信投影生成静态 HTML/JSON，不建设常驻服务。
- **代价**：首版交互能力有限。
- **收益**：保持本地优先、零账户、低运维，并验证用户是否真正需要更重界面。

## 5. 被动使用：环境式治理

### 5.1 用户体验

接入后的用户可以直接说：

```text
修复登录失败的问题。
```

Agent 读取项目入口时自动识别这是一个可能修改代码的请求，并在后台完成：

```text
自动恢复项目上下文
→ 创建任务状态与 Git 基线
→ 分类任务和风险
→ 对 Bug 先调查复现与根因
→ 形成最小范围与验证计划
→ 实施期间检查范围漂移
→ 收集真实验证证据
→ 生成关键变更解释包
→ 按风险决定是否需要人类理解/批准
→ 自动处理项目文件与 Wiki 候选
```

用户不再必须主动说“开始工作”或“收工”。这三句话继续保留，分别用于显式开工、恢复中断任务和手动关闭/诊断。

### 5.2 触发机制

被动触发采用三层能力，按可靠性递增：

1. **项目入口协议（默认、跨 Provider）**：接入生成的 `AGENTS.md` / `CLAUDE.md` managed block 要求 Agent 在任何写入意图前自动调用生命周期开始，在最终汇报前调用关闭检查。
2. **Manager Skill 路由（默认）**：Skill 识别“修复、实现、修改、重构、发布、迁移、删除”等写入意图，自动调用公开 Runtime；纯解释、只读审计和问答不创建任务。
3. **Provider Hook/Adapter（可选严格层）**：支持 hook 的工具可以在首次写文件前、最终回复前调用检查器。它提高强制性，但不成为事实源，也不作为基础产品的必需条件。

现实边界：如果某个 AI 工具完全不读取项目入口、不安装 Skill、也没有 hook，ObsidianToWiki 无法从操作系统层面截获它的文件修改。产品必须诚实报告当前工具的治理覆盖等级，不能假装绝对拦截。

### 5.3 低噪音提示策略

系统内部使用三种结果，不要求用户学习等级：

- **静默通过**：低风险、范围正常、证据充分。最终摘要中简短说明即可。
- **提醒但不中断**：出现新依赖、轻微范围漂移、值得学习的知识点或未覆盖的低风险验证。
- **必须确认**：根因不明却准备大改、P1/P0、删除/迁移/权限/支付/生产操作、严重范围漂移、证据失败、人类无法理解关键变化。

同一会话合并提醒，避免每改一个文件提示一次。

## 6. 任务状态与生命周期

### 6.1 本地任务状态

新增忽略提交的状态文件：

```text
.obsidiantowiki/task-state.json
```

最小 Schema：

```json
{
  "schema_version": 1,
  "task_id": "20260813-123000-login-failure",
  "status": "investigating",
  "request": "修复登录失败的问题",
  "task_type": "bug_fix",
  "risk": {"level": "P1", "reasons": ["authentication"]},
  "baseline": {
    "head": "<git-sha>",
    "dirty_paths": ["existing-file.md"],
    "captured_at": "<iso-time>"
  },
  "acceptance": ["过期令牌可刷新", "无权限请求仍被拒绝"],
  "scope": {
    "expected_paths": ["src/auth/", "tests/auth/"],
    "forbidden_paths": ["migrations/"],
    "rationale": "登录会话局部修复"
  },
  "bug": {
    "reproduction": "confirmed",
    "root_cause": "confirmed",
    "failing_evidence": ["test_refresh_expired_token"]
  },
  "verification_plan": ["unit", "api", "permission_negative"],
  "approvals": [],
  "evidence": [],
  "understanding": {},
  "knowledge_candidates": []
}
```

状态只保存任务控制事实，不复制源码、密钥或私人资料。

### 6.2 状态机

```text
detected
→ investigating
→ planned
→ awaiting_approval（按需）
→ implementing
→ verifying
→ awaiting_understanding（按需）
→ ready_to_close
→ closed
```

允许状态：

- `blocked`：无法复现、缺少环境或等待外部信息。
- `abandoned`：用户明确取消。
- `stale`：会话中断，下一次自动恢复。

没有根因的 Bug 可以从 `investigating` 进入 `blocked`，不能直接进入大范围 `implementing`。

### 6.3 中断恢复

下次打开项目时，如果发现未关闭状态：

```text
上次“修复登录失败”尚未关闭，当前停在“等待验证”。
我将先核对已有修改和测试状态，再继续。
```

如果 Git HEAD 或工作区与基线冲突，系统暂停自动继续，避免把其他会话修改算入当前任务。

## 7. 风险与自治策略

沿用项目现有 P3–P0，不另建等级：

| 风险 | 典型任务 | AI 自治 | 必要门禁 |
|---|---|---|---|
| P3 | 文档、文案、局部配置 | 自动执行 | 最小检查、范围正常 |
| P2 | 普通功能、局部 Bug | 自动计划与实施 | 根因/验收、定向测试、范围检查 |
| P1 | 登录、权限、核心业务、API 合同 | 计划后确认或按项目策略批准 | 正反路径、独立评审、理解确认、回滚说明 |
| P0 | 支付、删除、迁移、生产安全、不可逆操作 | 默认不自动实施 | 明确人工批准、专项证据、责任人、回滚/恢复演练 |

风险判断由规则与 Agent 共同完成。确定性命中（例如 migration、auth、payment、production）不能被 Agent 自行降级；误判可以由人说明理由后调整并记录。

## 8. Bug 根因与最小修改门禁

Bug 任务必须经过：

```text
复现 → 失败证据 → 根因 → 影响范围 → 最小方案 → 修复 → 原失败路径回归
```

关闭前必须满足：

- 有可重复复现，或明确写出为什么无法复现。
- `root_cause` 区分 `hypothesis / confirmed / unknown`。
- `unknown` 状态只允许诊断性修改，不允许重构式修复。
- 修复后重新执行原失败路径。
- 新增的异常捕获不能只是吞掉错误。
- 修改测试必须说明是修正错误断言还是新增回归覆盖。

范围检查不使用僵硬的“最多 N 个文件”作为唯一规则，而是比较：计划路径、实际路径、文件类别、依赖变化、删除、迁移、公共接口和架构边界。超出范围时先暂停并要求解释；合理发现可以更新任务契约，不合理扩张必须撤销或拆分。

## 9. 结构化证据与独立验证

现有 `--verification` 自由文本升级为证据记录，同时保留兼容读取：

```json
{
  "kind": "unit_test",
  "command": "python -m unittest tests.test_auth -v",
  "exit_code": 0,
  "result": "passed",
  "executed_at": "<iso-time>",
  "actor": "deterministic_check",
  "artifact": "",
  "covers": ["expired token", "invalid token"],
  "limitations": []
}
```

证据来源分为：

- `deterministic_check`：编译、测试、lint、扫描、HTTP/DB/浏览器结果。
- `self_review`：实施 Agent 自审，只能作为补充。
- `independent_ai_review`：隔离上下文或独立审查者。
- `human_review`：人的理解与批准。

系统不相信仅由自然语言声称的“测试通过”。能捕获退出码时自动捕获；无法自动执行的手工验证必须记录步骤、观察结果和执行者。

## 10. 人类理解门禁

### 10.1 关键变更解释包

解释包必须基于任务状态和实际 Diff，至少包括：

1. 用户问题和最终根因。
2. 修改的文件与每个文件的作用。
3. 核心数据流或调用链变化。
4. 为什么选择当前方案，以及被否决方案。
5. 边界条件和最可能失败的位置。
6. 测试证明了什么、没有证明什么。
7. 残余风险和回滚方法。
8. 新增依赖、接口、配置、迁移或权限影响。

解释分两层显示：先给普通用户可理解的 6–10 行摘要；用户展开后查看技术细节和具体 Diff。

### 10.2 门禁规则

- P3：不阻塞，只给修改摘要。
- P2：自动提供解释包；范围异常或新知识点明显时提醒。
- P1：关闭前必须记录“人已看到核心变化和残余风险”。
- P0：实施前和发布前均需人工批准；批准必须绑定当前任务状态和 Diff 哈希，代码变化后旧批准失效。

理解确认不是让用户假装读懂全部代码。系统必须允许用户回答“我没理解”，随后提供更简单解释、调用链、示例或要求拆小变更。无法解释清楚的高风险代码不能上线。

## 11. 能力恢复闭环

### 11.1 目标

能力恢复不是强迫用户重写全部代码，而是持续恢复四类能力：

- 阅读：看懂入口、调用链和关键判断。
- 诊断：从现象、日志、失败测试定位根因。
- 设计：判断范围、边界与方案取舍。
- 验证：知道什么证据能证明或推翻实现。

### 11.2 自适应介入

系统不在每个任务后考试。只在以下情况提示：

- P1/P0 高风险任务。
- 用户首次接触某类核心机制。
- 同一模块反复让 AI 修复。
- AI 方案被人否决或发生明显错误。
- 系统发现用户连续多次直接接受而从未查看解释。

提示保持轻量：

```text
本次最值得掌握的是“刷新令牌后必须同步替换缓存”。
你可以：
1. 看 2 分钟解释（推荐）
2. 先说说你的理解，我来补充
3. 这次跳过
```

用户可以跳过；P1/P0 的风险确认不能跳过，但学习练习本身不作为发布阻塞。

### 11.3 能力记录

任务关闭时生成候选，而不是自动永久写入：

```json
{
  "topic": "会话令牌刷新",
  "learned": ["刷新后同步缓存"],
  "gaps": ["并发刷新控制"],
  "ai_mistakes": ["最初只修改前端重试"],
  "next_practice": "独立解释一次过期令牌调用链",
  "destination": "personal",
  "requires_confirmation": true
}
```

确认后写入私人 Wiki `10_personal/`；项目根因和维护风险进入项目 Wiki；跨项目治理模式才进入 `30_shared/`。

### 11.4 防止形式化

不能用“生成一篇 AI 教程”冒充能力恢复。有效信号包括：

- 用户能指出核心入口和失败点。
- 用户能判断一个方案为何扩大范围。
- 用户能解释测试覆盖与未覆盖内容。
- 下一次相似问题中，人先提出的诊断方向更准确。

系统只记录可观察行为，不给用户打虚假的“能力分数”。

## 12. 补丁循环与架构腐化预警

第一版使用保守信号，不自动重构：

- 同一文件/模块在最近若干已关闭任务中反复修改。
- 同一失败现象或测试多次重新出现。
- 多次新增相似条件分支或异常兜底。
- 每次修复的实际范围持续扩大。
- 根因长期保持 `unknown` 或反复变化。

触发后输出：

```text
该区域近期已连续修复 3 次，且每次范围扩大。
建议停止局部补丁，创建“根因复盘/边界重审”任务。
```

这里只生成建议和任务候选，不自动改架构。

## 14. 异常与失败处理

- **工作区任务前已脏**：保存基线路径，禁止误算成本任务改动。
- **并发会话**：检测不同 task id 和 HEAD；不自动合并状态，要求选择恢复或新建任务。
- **状态损坏**：保留文件，报告修复建议；不得静默重置。
- **无法复现 Bug**：进入 blocked/investigating，允许诊断，不宣告修复。
- **验证工具不可用**：记录 blocker 和残余风险；P1/P0 不得降级为“口头通过”。
- **用户不理解**：重新解释或拆小；高风险不关闭。
- **Wiki 不可用或损坏**：P3/P2 使用 L0/L1 降级，P1/P0 在需要历史事实时 fail-closed；禁止模型补猜。
- **页面超过预算**：停止把整页注入上下文，先运行记忆编译器；编译失败则使用最近可信投影并标记 degraded。
- **记忆候选冲突**：保留现有 active 卡片，新候选进入 disputed/review，不允许 AI 自动覆盖。
- **驾驶舱生成失败**：不影响耐久 Markdown 和工程门禁；用户仍可通过自然语言与 Markdown 深度入口访问。
- **Agent 未调用治理**：下一次项目入口检查发现 diff 无任务基线，标记为 ungoverned changes，并要求补做范围和证据审计。
- **用户取消**：标记 abandoned，保留本次修改归属，不擅自删除或回滚。

## 17. 验收场景

### 场景 A：用户完全不提 ObsidianToWiki

用户说“修复设置页保存失败”。Agent 自动创建任务、保存基线、调查、实施、验证、解释并关闭。用户只在出现范围漂移时收到一次提醒。

### 场景 B：简单 Bug 被 AI 扩大

计划只修改 `settings/service.py` 和测试，实际触碰认证、迁移和 18 个文件。系统阻止继续，要求解释、拆分或重新批准。

### 场景 C：AI 没找到根因

Bug 无法复现，AI 准备加入通用 try/except。系统阻止其作为正式修复，只允许日志/诊断改动并标记未完成。

### 场景 D：P1 登录变更

系统要求正反路径、独立评审、关键变更解释和人的风险确认。用户选择“没理解”时，系统重新解释而不是直接关闭。

### 场景 E：能力恢复

系统发现用户连续多次让 AI 修会话问题，推荐一个 2 分钟调用链解释和一次“先说根因”的轻量练习；用户确认后将能力缺口与学习结果写入私人 Wiki。

### 场景 F：中断与下一次恢复

会话中断后，下一 Agent 自动发现未关闭任务、核对 HEAD/diff 和证据，继续原状态；不会把其他并发修改混入。

### 场景 G：项目接入后长期没有记录

系统发现核心页仍是模板空壳，从当前项目控制文件和 Git 生成一份 `review_required` 首次快照；用户只确认关键边界，不需要手工填写七个页面。

### 场景 H：长期项目记忆已经膨胀

系统对旧核心页先做备份和解析预演，把当前有效事实转成原子卡，将旧叙事归档，再生成有界当前投影。迁移前后所有来源可追溯，原文件不被静默覆盖。

### 场景 I：Wiki 损坏或检索无结果

损坏页面进入隔离，模型只得到 L0/L1 和明确的缺失声明。P2 局部修复可以降级继续；P1 鉴权任务因缺少必要历史约束被阻断，AI 不得自行补全。

### 场景 J：用户不打开 Obsidian

用户通过自然语言询问当前状态，并在本地驾驶舱看到最近变化、风险、待决定和下一步。只有查看依据时才下钻到 Markdown、Diff 和任务证据。

## 18. 成功指标

首轮真实试点观察：

- 写入型请求被动建档率。
- 无基线 Diff 的发现率。
- Bug 有复现与根因记录的比例。
- 范围漂移被发现后撤回、拆分或批准的结果。
- 非结构化“已测试”被阻止的比例。
- P1/P0 独立证据和人工确认完整率。
- 用户查看解释、选择“不理解”或展开技术细节的实际行为。
- 产生并获确认的个人知识候选数量。
- 低风险任务增加的平均交互次数，目标是接近零额外打断。
- 关闭任务产生可判定记忆候选的比例，以及候选被去重/替代/拒绝的原因分布。
- 空模板项目比例，目标是接入并首次开发后为零。
- 核心当前投影预算超限率，目标是零；超限必须编译而不是截断。
- 每次任务实际注入的 Wiki token 中位数和 P95，不能随项目年龄线性增长。
- Context Receipt 完整率和损坏/过期/冲突页面被隔离率。
- 用户无需打开 Obsidian 即可回答“当前状态、最近变化、风险、下一步”的成功率。
- 驾驶舱行动项被处理率；不以 Markdown 打开次数作为成功指标。

不使用生成代码行数、Token 消耗或完成任务数量作为核心成功指标。

## 19. 最终定义

本次迭代完成后，ObsidianToWiki 不再只是“用户想起来才调用的 Markdown 项目记忆工具”，而成为接入项目的环境式工程控制与记忆编译层：

> 平时自动记录、验证、压缩并按需呈现；让 AI 只看到当前可信且有预算的上下文，让人只看到需要理解和决定的内容；在 AI 可能乱做、记忆可能失真或工程责任需要人承担时，及时停下来让人重新取得控制权。
