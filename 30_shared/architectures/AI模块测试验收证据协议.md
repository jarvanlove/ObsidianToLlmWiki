# AI模块测试验收证据协议

## 1. 目标

代码写完不等于任务完成。

AI coding 任务必须用证据证明：

- 用户路径能跑通。
- 前后端链路能跑通。
- 数据库或外部服务在真实环境下能跑通。
- 权限、错误态、空状态和异常输入有检查。
- 浏览器控制台没有应用自身错误。
- 项目控制文件和长期 Wiki 结论按边界更新。

本协议用于补充 `TESTING.md`、`TASKS.md`、项目级 `AGENTS.md` / `CLAUDE.md`，并作为任务执行和收工提示词的测试验收依据。

对于 U1+ UI 任务，还必须遵守 [[30_shared/architectures/AI产品UI设计治理协议|AI产品UI设计治理协议]]：U2/U3 在方向批准前不进入生产实现，收工前保留视觉证据。

## 2. 分层验收模型

涉及哪一层，就必须验证哪一层。不能因为单元测试通过就关闭一个有页面、API、数据库或权限的模块。

| 层级 | 覆盖内容 | 常见验证方式 | 关闭任务前的最低证据 |
|---|---|---|---|
| L0 静态检查 | 格式、类型、lint、构建 | `lint`、`typecheck`、`build`、语言检查器 | 命令和结果 |
| L1 单元测试 | 纯函数、schema、状态转换、权限判断 | 单元测试框架 | 成功和失败路径 |
| L2 API/服务测试 | 请求响应、错误码、认证、service 层 | API 测试、TestClient、HTTP client | 成功、失败、未登录或无权限 |
| L3 真实数据层 | migration、seed、真实数据库 schema、唯一约束、外键 | 本地真实 DB smoke、迁移命令、查询检查 | 真实环境读写或明确不涉及 |
| L4 前后端集成 | 浏览器操作 -> API -> 数据 -> UI 状态 | HTTP smoke、浏览器自动化 | 关键用户路径结果 |
| L5 浏览器 QA | 页面加载、console、hydration、响应式、交互状态 | Playwright、gstack、无插件 Chrome | 控制台结果和关键页面状态 |
| L6 安全/权限 | auth、role、secret、敏感数据、越权 | targeted tests、人工 checklist | 正向和反向权限检查 |
| L7 数据质量 | 来源、口径、置信度、冲突、人工确认 | 样本数据、断言、人工复核 | 数据来源和可信状态 |
| L8 文档回写 | 控制文件、项目 Wiki、共享层 | diff 检查、索引重建 | 更新或说明无需更新 |

## 3. 模块完成 Definition of Done

任一模块、Slice 或关键 Bug 修复完成前，AI 必须能回答：

1. 用户从哪个入口进入？
2. 用户执行了什么操作？
3. 前端调用了哪些 API？
4. API 读取或写入了哪些数据？
5. 成功后页面或数据如何变化？
6. 失败后如何提示？
7. 未登录或无权限时如何表现？
8. 空数据、重复数据、非法数据如何表现？
9. 控制台是否有应用自身错误？
10. 本次验证使用的是模拟环境还是真实环境？
11. 哪些风险未验证，为什么可以暂时接受？
12. 哪些项目控制文件或 Wiki 页面需要更新？

如果这些问题答不上来，任务不能标记为完成，只能标记为部分完成或有残留风险。

## 4. UI 和浏览器验收

涉及页面、交互、登录、跳转、图表或表单时，必须进行浏览器级验证。

最低要求：

- 页面能在本地指定端口打开。
- 登录态、跳转、表单提交或关键交互可用。
- 控制台无应用自身 `error`。
- 无 React hydration mismatch。
- 失败、加载、空状态和禁用状态可见。
- 受保护页面的未登录访问被拦截。
- 桌面和移动宽度无明显遮挡、溢出、重叠。

U1+ 任务还必须把以下内容记录在项目 `docs/design/ui-tasks/<id>.yaml`：

- 已批准的设计来源，或说明本次只在既有系统内修改。
- 固定视口截图。
- 独立 Visual QA 报告，包含 P0/P1/P2 与结论。
- 无障碍自动检查或可重复的手工证据。

U2/U3 未保存视觉方向批准记录时，不能以实现、lint 或截图代替批准；U3 还必须保存 Design RFC 批准。

浏览器扩展干扰处理：

- 如果 hydration mismatch 中出现非项目属性，例如 `cz-shortcut-listen="true"`，优先怀疑浏览器插件注入。
- 必须用无插件浏览器上下文复测。
- 无插件不复现，记录为插件干扰；必要时在根布局做最小范围抑制，避免开发控制台被噪音污染。
- 无插件仍复现，按应用 Bug 修复，不允许关闭任务。

## 5. API、数据库和真实环境验收

涉及后端、数据库、认证、文件、外部服务时，不能只依赖 mock 或内存数据库。

必须检查：

- API 成功路径。
- API 失败路径。
- 未登录或无权限路径。
- 本地真实环境变量能启动服务。
- 本地真实数据库 migration/seed 能运行。
- 至少一个真实 HTTP 请求链路能跑通。
- 如果引入新环境变量，`.env.example` 和文档必须同步。

如果无法运行真实环境验证，必须在最终报告中说明：

- 为什么无法运行。
- 哪些风险未覆盖。
- 后续谁来验证。

## 6. Bug 修复验收

Bug 修复固定流程：

```text
复现 -> 定级 -> 定位根因 -> 最小修复 -> 回归验证 -> 记录防复发规则
```

要求：

- 没有复现路径，不做大范围改动。
- 没有根因，不做重构式修复。
- 修复后必须重跑失败路径。
- 如果无法补自动化测试，至少留下可重复的手工验收步骤。
- 如果 Bug 暴露出项目流程问题，更新 `TESTING.md` 或共享验收协议。

## 7. 证据记录格式

任务关闭或收工时，至少记录：

```text
验证命令：
- ...

真实链路：
- API:
- DB:
- Browser:

关键结果：
- ...

未验证风险：
- ...

文档回写：
- ...
```

最终汇报不能只写“已测试”或“已完成”，必须写清楚具体命令、路径、结果和剩余风险。

## 8. 何时回写共享层

只有跨项目可复用的经验才写入 `30_shared`，例如：

- 新的测试验收门禁。
- 重复出现的 Bug 排查模式。
- AI 任务执行/收工协议缺口。
- 项目控制文件模板需要升级。
- 安全、权限、数据、发布流程的通用规则。

不要把某个项目的账号、端口、业务数据、客户材料或一次性日志写入共享层。
