# AI任务执行提示词

## 使用场景

项目已经接入 wiki，并且需要继续推进某个具体任务时使用。

## 用户只需要说

```text
继续。
```

或者：

```text
做 TASKS.md 里的下一个任务。
```

如果你已经知道任务，也可以说：

```text
处理这个任务：<任务描述或任务ID>。
```

## Agent 内部执行协议

Agent 应自动完成以下动作，不要求用户背入口文件或读取顺序：

1. 恢复项目上下文和当前任务状态。
2. 确认任务边界、风险等级和影响范围。
3. 如果需求不清或风险较高，先问用户。
4. 如果可以执行，按最小方案实现。
5. 只修改与任务直接相关的文件。
6. 不做无关重构，不新增无关功能。
7. 根据 [[30_shared/architectures/AI模块测试验收证据协议|AI模块测试验收证据协议]] 判断本任务涉及哪些测试层级。
8. 运行最小但充分的验证，并保留命令、真实链路和未验证风险。
9. 更新任务状态、必要项目控制文件和项目 wiki。

UI 任务追加规则：

- U1 只在已批准系统内修改，不借机重塑页面。
- U2/U3 先记录视觉方向、参考和反例；未获批准不得写生产页面。
- 用户点名的 UI Skill 必须记录为执行器，不得覆盖项目 Contract。
- U1+ 完成后记录截图、Visual QA 和无障碍证据。

## 执行前测试计划

实现前先给出本任务的验证计划：

```text
变更层级：
- UI:
- API:
- DB:
- 权限:
- 数据:
- AI/外部服务:

计划验证：
- 静态检查:
- 单元/API:
- 真实 HTTP:
- 真实 DB:
- 浏览器 smoke:
- 权限/错误态:
```

如果任务是 Bug 修复，必须先写清：

- 复现路径。
- 影响范围。
- 可能根因。
- 最小修复范围。
- 回归验证路径。

没有复现路径时，不应做大范围重构式修复。

## 完成后汇报

汇报应包含：

- 做了什么。
- 修改了哪些文件。
- 行为变化是什么。
- 运行了哪些验证，具体命令和结果是什么。
- 真实 HTTP、真实 DB、浏览器 smoke 是否跑过。
- UI 相关任务的控制台和 hydration 结果。
- 剩余风险是什么。
- 是否需要用户决策。
