# AI 团队协作项目工作流

## 定位

这是一个实践中的共享模式，当前版本为 v0.2。它来自一组真实项目的个人 AI 工作流实践，以及 ZOE Company Website 项目的多人 AI 协作准备工作。

它适合这些场景：

- 团队成员编码能力弱，主要通过 AI 完成开发。
- 项目负责人不参与每日开发，但最后要验收、修复、继续迭代。
- 多人会同时修改同一个仓库，且存在共享后端、公共文档、公共配置。
- 希望项目结束后沉淀出可复用的 AI 团队协作方法，而不是只留下聊天记录。

核心判断：

```text
个人 AI 工作流 = 每个人完成自己任务的执行原子。
团队 AI 工作流 = 组织多个执行原子并控制冲突、记忆、验收和集成的项目控制面。
```

因此，团队协作不是取代个人工作流，而是在个人工作流外面增加角色、分支、边界、集成、验收和记忆机制。

## 实践来源

本模式不是凭空设计，来自多类项目实践。开源模板中仅保留泛化类型，不保留个人项目名称、路径、账号或客户材料。

| 项目 | 提炼出的关键经验 |
|---|---|
| 内容社区类项目 | 垂直切片开发有效：每个 Slice 都包含数据库、API、页面、联调和验收，适合 AI 逐步推进。 |
| 工业/实训类交付项目 | 大项目必须把 PRD、模块文档、设计规范、目录索引、AI 生命周期分层，否则 AI 会遗漏页面和边界。 |
| 高复杂度业务工作台 | 高复杂度项目需要“证据链”：真实命令、HTTP smoke、浏览器 smoke、数据检查、AI 输出确认、过程记录。 |
| 批量验收型项目 | 批量项目必须先建立模板、PRD 审批门、开发计划、AI 可执行任务拆分，再允许实现。 |
| 官网/后台多人协作项目 | 多人协作必须增加个人分支、个人任务文档、组长集成、共享服务边界、Git 防误操作和项目过程记忆。 |

这些实践说明：AI 协作的关键不是“文档越多越好”，而是让 AI 在每次行动前能准确知道：

```text
我是谁 -> 在哪个分支 -> 负责什么 -> 不能碰什么 -> 怎么验证 -> 更新哪里 -> 提交给谁
```

## 与共享架构层的关系

本工作流不是孤立规则，必须服从 `30_shared/architectures/` 中已有协议：

| 共享架构协议 | 在团队协作中的作用 |
|---|---|
| [[30_shared/architectures/AI项目级约束文件结构|AI项目级约束文件结构]] | 定义 `AGENTS.md`、`CLAUDE.md`、`PRODUCT_SPEC.md`、`ARCHITECTURE.md`、`TASKS.md`、`TESTING.md` 等项目控制文件职责，团队项目不能绕过这些入口。 |
| [[30_shared/architectures/AI-coding生命周期控制协议|AI coding 生命周期控制协议]] | 定义 `task_start -> task_plan -> task_implement -> task_verify -> task_close -> memory_file_back`，个人任务和组长集成都要按这个生命周期闭环。 |
| [[30_shared/architectures/AI模块测试验收证据协议|AI模块测试验收证据协议]] | 定义 L0-L8 分层验收证据，团队任务不能只以“代码写完”或“页面打开”为完成标准。 |
| [[30_shared/architectures/资料摄入质量协议|资料摄入质量协议]] | 当学生或组长新增资料、素材、需求文档、客户材料时，必须保留来源、结构、引用和沉淀路由，不能只写泛泛摘要。 |

团队工作流负责“多人如何协作”；共享架构协议负责“AI 项目控制面如何成立”。两者必须一起生效。

## 目标

- 人少读文档，AI 多读规则。
- 每个成员只需要先看自己的入口文档，公共规则由 AI 读取。
- 仓库成为团队协作记忆源，不依赖个人聊天记录、模型上下文或项目负责人脑内记忆。
- 公共代码、共享服务和公共文档有明确冲突治理。
- 每个任务都有验收标准、验证命令、证据和回写位置。
- 组长能集成组内成果，项目负责人能最终验收和继续迭代。
- 项目结束后能沉淀到个人 Wiki 共享层，成为下一次团队协作的模板。

## 控制面结构

```text
project/
├─ README.md                         # 人和 AI 的项目总入口，必须有树状结构和目录说明
├─ AGENTS.md                         # Codex 项目级入口，写本项目事实、边界、验证和禁止项
├─ CLAUDE.md                         # Claude Code/兼容工具入口，与 AGENTS 同步项目事实
├─ PRODUCT_SPEC.md                   # 产品目标、范围、非目标、验收口径
├─ ARCHITECTURE.md                   # 架构、模块边界、共享服务、数据流、技术决策
├─ TASKS.md                          # 项目级任务、阶段状态、阻塞和下一步
├─ TESTING.md                        # 验证命令、测试分层、手工验收路径
├─ docs/
│  ├─ README.md                      # docs 目录索引，新增文档必须同步
│  ├─ human/                         # 给人看的短入口
│  ├─ ai/                            # 给 AI 读的协作规则树
│  ├─ students/                      # 每个人的专属任务入口
│  ├─ handoff/                       # 分组、任务、Git、验收、交付、技术边界
│  └─ project/                       # 过程记忆、仓库盘点、阶段总结
├─ scripts/git/                      # 防误提交、防错分支、发布辅助脚本
└─ wiki.context.json                 # 个人 Wiki 接入信息，仅本地/项目负责人使用
```

要求：

- 每个有 README 的目录都应使用树状结构说明目录和文件职责。
- 没有 README 的关键目录，应补一个最小索引。
- 文档不是主要给学生背的，而是给 AI 定位、排错、验收、回写用的。
- 人类入口必须短，AI 入口必须精确。

## 分支模型

```text
main                    # 旧系统或稳定基线，禁止普通成员提交和合并
dev                     # 项目负责人总集成分支
team/<group>            # 组长集成分支
<group>/<id>-workspace  # 个人工作分支
```

规则：

- `main` 只由项目负责人处理，团队成员和 AI 不合入。
- 学生只在个人分支提交。
- 组长把个人分支集成到 `team/<group>`。
- 项目负责人或指定集成人把 `team/<group>` 合到 `dev`。
- 公共服务改动必须在个人任务中声明影响范围，并在组长集成时重点复查。
- 公共文档只做必要更新，避免每个人同时改同一份大文档。

## 角色分层

| 角色 | 责任 | 主要文件 |
|---|---|---|
| 项目负责人 | 定目标、定边界、最终验收、合入 `main`、沉淀 Wiki | `README.md`、`TASKS.md`、`docs/project/progress-log.md`、Wiki |
| 组长 | 拆组内任务、收个人分支、解决冲突、组内验收、更新组进度 | `docs/handoff/assignments.md`、`docs/project/progress-log.md` |
| 组员 | 在个人分支完成个人任务、验证、提交、更新个人任务状态 | `docs/students/<id>.md`、`docs/handoff/assignments.md` |
| AI | 读取规则、执行任务、验证、更新必要文档、生成提交说明 | `AGENTS.md`、`CLAUDE.md`、`docs/ai/` |

## 个人任务闭环

```text
确认身份和分支
-> 同步来源分支
-> 读取 AI 规则
-> 读取个人任务文档
-> 输出短计划和影响范围
-> 实现
-> 验证
-> 更新个人任务状态
-> 必要时更新公共索引或局部 README
-> 提交个人分支
-> 汇报组长
```

映射到生命周期协议：

| 生命周期节点 | 个人任务中必须做什么 |
|---|---|
| `task_start` | 确认身份、分支、任务、风险等级、影响范围。 |
| `task_plan` | 输出短计划、预计修改文件、验收标准和验证层级。 |
| `task_implement` | 只实现个人任务范围，不做无关重构。 |
| `task_verify` | 按 L0-L8 选择验证，记录命令、真实链路和未验证风险。 |
| `task_close` | 更新个人任务状态、必要 README/索引、提交个人分支。 |
| `memory_file_back` | 只有跨项目可复用结论才写回 Wiki 共享层；个人流水账留在仓库。 |

个人任务关闭时，至少要说明涉及哪些验收层级：

```text
L0 静态检查：
L1 单元测试：
L2 API/服务测试：
L3 真实数据层：
L4 前后端集成：
L5 浏览器 QA：
L6 安全/权限：
L7 数据质量：
L8 文档回写：
```

个人任务结束必须交付：

- 做了什么。
- 改了哪些文件。
- 跑了哪些验证。
- 哪些没有验证，原因是什么。
- 是否碰到共享服务、公共文档、公共配置。
- 下一步建议。

## 组长集成闭环

```text
确认组分支
-> 拉取个人分支
-> 查看个人提交和任务说明
-> 合并一个人
-> 解决冲突或退回
-> 运行组内验证
-> 更新 assignments
-> 重大事件写 progress-log
-> 推送 team/<group>
-> 汇报给项目负责人
```

组长不要一次性合并所有人。一个人一合、一验、一记录，出问题时才能定位。

组长集成也必须走生命周期：

- `task_start`：确认本次集成哪些个人分支。
- `task_plan`：确定合并顺序和冲突风险。
- `task_implement`：一次只合一个人。
- `task_verify`：跑组内受影响范围验证，重点检查共享 `server/`、公共文档、API、环境变量。
- `task_close`：更新 `assignments.md` 和必要 `progress-log.md`。
- `memory_file_back`：阶段复盘时再把可复用经验提升到共享层。

## 过程记忆

仓库本身必须成为协作记忆源。推荐分层：

| 文件 | 记录什么 | 更新时机 |
|---|---|---|
| `docs/handoff/assignments.md` | 人员、分支、个人任务、状态、下一步 | 个人任务结束、组长调整任务 |
| `docs/project/progress-log.md` | 阶段事件、组长集成、重大风险、验收结论 | 组长集成、阶段验收、返工、重大问题 |
| `TASKS.md` | 项目级任务状态、里程碑、阻塞 | 阶段变化、项目负责人验收、范围变化 |
| `CHANGELOG.md` | 可发布版本变化 | 形成可交付版本时 |
| `ARCHITECTURE.md` / ADR | 架构和边界变化 | 技术路线、共享服务、数据模型、权限变化 |
| Wiki 共享层 | 可跨项目复用的模式 | 阶段复盘或项目结束后沉淀 |

不要把所有流水账都写进 Wiki。Wiki 只保存可复用结论、关键决策和经验模式；项目仓库保存日常协作过程。

## 公共文档冲突策略

多人项目中，公共文档最容易冲突。推荐规则：

- 每个人优先更新自己的 `docs/students/<id>.md` 或任务状态行。
- `assignments.md` 允许个人更新自己的行，但不要重排全表。
- `progress-log.md` 主要由组长或项目负责人更新。
- `README.md`、`AGENTS.md`、`CLAUDE.md`、`ARCHITECTURE.md`、`TESTING.md` 由组长或项目负责人更新，普通成员只在任务明确要求时改。
- 新增文档时必须更新最近一级 README 和 `docs/README.md`。
- 冲突时不要让 AI 盲目选择 ours/theirs，应停止并说明冲突文件、冲突语义和建议保留内容。

## 共享服务冲突策略

如果多个组共用一个后端或服务层：

- 每个任务必须声明是否改共享服务。
- 改接口必须同步 API 文档、测试和调用方。
- 改数据库模型必须声明迁移、种子数据和兼容影响。
- 组长集成时优先验证共享服务，再验证各自前端。
- 公共服务的“格式化全文件”“重命名大范围目录”“无关重构”默认禁止。
- 跨组影响必须写入 `progress-log.md`，不能只在聊天中说。

## 防失控规则

- Git 脚本拒绝在受保护分支直接提交。
- GitLab 保护 `main`、`dev`、team 分支。
- 公共文档只允许最小必要更新。
- 共享后端或共享服务改动必须声明影响范围并跑检查。
- 冲突时 AI 停止提交，不盲目覆盖 ours/theirs。
- 不提交 `.env`、token、密码、本机绝对路径、私人 Wiki 内容。
- 不允许 AI 在未读个人任务文档和协作规则时直接写代码。
- 不允许把“页面能打开”当成完成，必须满足验收标准和无控制台/接口错误。
- 不允许弱化 [[30_shared/architectures/AI模块测试验收证据协议|AI模块测试验收证据协议]]；项目 `TESTING.md` 可以更具体，但不能比 L0-L8 更低。

## 给学生的最短提示词

```text
我是 <姓名/代号>，在 <个人分支>。
请先读取 AGENTS.md、docs/ai/README.md、docs/students/<代号>.md 和 docs/handoff/assignments.md。
只做分配给我的任务。
先输出 5 行以内计划和影响范围，不要直接写代码。
完成后运行必要验证，更新我的任务状态，提交并推送我的个人分支。
```

## 给组长的最短提示词

```text
我是 <组名> 组长。
请读取 AGENTS.md、docs/ai/README.md、docs/handoff/assignments.md、docs/handoff/team-lead-guide.md。
逐个检查组员个人分支，按一个人一合并一验证一记录的方式集成到 team/<group>。
遇到冲突先解释冲突语义，不要盲目覆盖。
集成完成后更新 assignments.md 和必要的 progress-log.md。
```

## 给项目负责人的验收提示词

```text
请基于 dev 分支做阶段验收。
先读取 README.md、TASKS.md、TESTING.md、docs/handoff/assignments.md、docs/project/progress-log.md。
输出：已完成范围、未完成范围、验证结果、主要风险、需要返工的任务、是否具备合入 main 的条件。
不要合入 main，除非我明确要求。
```

## 成熟度分级

| 等级 | 状态 | 特征 |
|---|---|---|
| L0 | 聊天协作 | 任务散在聊天里，无法追溯。 |
| L1 | 个人工作流 | 单人项目有控制文件、任务、验证、Wiki 回写。 |
| L2 | 文档化团队协作 | 有分支、个人文档、组长规则、过程记忆。 |
| L3 | 工程化团队协作 | 有 Git 保护、脚本、CI、验收证据、冲突治理。 |
| L4 | 可复制组织模式 | 项目结束后沉淀到共享 Wiki，可直接复制到新项目。 |

ZOE Company Website 当前处于 L2，并正在补 L3。

## 复盘标准

项目结束后必须复盘：

- 个人文档是否真的降低学生理解成本。
- AI 是否稳定遵守读取顺序和分支规则。
- `assignments.md` 是否足以追踪个人任务。
- `progress-log.md` 是否足以支撑项目负责人最终验收。
- 冲突规则是否降低公共文档和共享服务冲突。
- 组长是否能在不依赖项目负责人每日介入的情况下完成集成。
- 项目负责人是否能只靠仓库记忆恢复项目全貌。
- 哪些规则应该提升为下一次项目模板或 Wiki 共享层模式。
