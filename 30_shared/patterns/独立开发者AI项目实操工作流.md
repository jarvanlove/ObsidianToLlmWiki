# 独立开发者AI项目实操工作流

## 0. 目标

适用场景：

```text
一个人负责一个项目 0-1。
你同时负责需求、原型、设计、前端、后端、数据库、开发、测试、部署、运维、文档、推广、销售。
主要工具是 Codex 和 Claude Code。
项目会持续变更需求。
```

最终目标不是“让 AI 写完所有代码”，而是建立一个可重复流程：

```text
想法 -> 规格 -> 原型 -> 架构 -> 任务 -> 实现 -> 验证 -> 发布 -> 反馈 -> 迭代
```

每一步都有文件承载、AI 输入、验收条件和下一步出口。

## 0.1 2026-07 实践升级结论

6 月版本解决了“一个人如何从 0-1 驱动 AI 做项目”。过去一个月在多个项目上实践后，需要补充一个更精确的判断：

```text
AI 项目能否长期稳定推进，不取决于文档数量，而取决于项目控制面是否完整。
```

项目控制面包括：

```text
入口文件 -> 产品边界 -> 架构边界 -> 任务状态 -> 验证证据 -> 过程记忆 -> Wiki 沉淀
```

不同项目沉淀出的经验。开源模板中仅保留泛化类型，不保留个人项目名称、路径、账号或客户材料：

| 项目 | 对个人工作流的修正 |
|---|---|
| 内容社区类项目 | 垂直切片比“大模块一次性写完”更稳。每个 Slice 必须端到端覆盖数据、API、页面、联调和验收。 |
| 工业/实训类交付项目 | 大型旧系统或交付项目必须有 docs 索引、模块拆分、设计边界和 AI 生命周期，否则 AI 会遗漏未截图页面、隐藏模块和交付边界。 |
| 高复杂度业务工作台 | 复杂业务必须保留验收证据链：测试命令、HTTP smoke、浏览器 smoke、数据检查、AI 输出确认、风险记录。 |
| 批量验收型项目 | 批量项目不能直接开写，必须先经过需求调研、PRD 审批、开发计划、AI 可执行任务拆分和统一模板。 |
| 官网/后台多人协作项目 | 个人工作流可以扩展成团队工作流；团队协作的执行单元仍然是一个人的任务闭环。 |

因此，个人 AI 工作流现在应理解为：

```text
用户自然语言入口
-> AI 自动读取项目控制面
-> 按最小任务或垂直切片执行
-> 以验证证据关闭任务
-> 将过程记忆留在仓库
-> 将可复用结论沉淀到 Wiki
```

## 0.2 仓库即记忆源

聊天记录和模型上下文不能作为项目记忆。真正可靠的是仓库内的文件。

推荐分层：

| 文件/目录 | 作用 |
|---|---|
| `README.md` | 人和 AI 的总入口，必须有树状项目结构和关键目录说明。 |
| `AGENTS.md` / `CLAUDE.md` | AI 工具入口，写本项目事实、边界、验证、禁止项。 |
| `PRODUCT_SPEC.md` | 产品目标、范围、非目标、验收口径。 |
| `ARCHITECTURE.md` | 技术栈、模块、数据流、共享服务、稳定边界。 |
| `TASKS.md` | 当前任务、状态、阻塞、下一步。 |
| `TESTING.md` | 验证命令、手工验收路径、测试分层。 |
| `docs/README.md` | 文档目录索引，新增文档必须同步。 |
| `docs/adr/` | 重大技术或流程决策。 |
| `docs/project/` 或 `project.memory.md` | 过程记忆、阶段总结、仓库盘点。 |
| Wiki | 跨项目可复用结论、模式、架构、提示词。 |

规则：

```text
仓库记录项目事实和过程。
Wiki 记录可复用结论和长期记忆。
聊天只负责交互，不作为唯一依据。
```

## 0.3 低失误率的关键机制

实践中最能降低 AI 失误率的机制：

- 先定边界再写代码：PRD、非目标、架构边界、禁止项必须存在。
- 垂直切片推进：一个 Slice 能独立运行、独立验证、独立关闭。
- 任务有验收标准：不能用“做完了”“页面能打开”代替验收。
- 验证有证据链：命令、截图、HTTP smoke、浏览器 smoke、数据检查按风险选择。
- 文档有索引：AI 不靠猜文件名找上下文。
- 目录有 README：每层目录都告诉 AI 文件放什么、什么时候更新。
- 重大决策写 ADR：避免同一个问题反复争论或反复改方向。
- 收工时回写：更新任务、风险、验证、下一步，而不是只在聊天里汇报。
- Wiki 只沉淀可复用结论：不要把所有项目流水账灌进共享层。

## 0.4 个人工作流和团队工作流的关系

团队协作不是另一套完全不同的方法。它是在个人工作流外面增加协作控制层。

```text
个人工作流解决：一个人怎么让 AI 稳定完成一个任务。
团队工作流解决：十个人怎么在一个仓库里各自完成任务、互不覆盖、可追溯、可集成、可验收。
```

所以个人工作流是团队工作流的原子单元。每个学生、组长、项目负责人本质上都在执行个人工作流，只是读取的入口、分支、权限和回写位置不同。

## 0.5 必须继承的共享架构协议

个人工作流不是一篇孤立操作手册。实际执行时必须继承共享架构层：

| 协议 | 对个人工作流的约束 |
|---|---|
| [[30_shared/architectures/AI项目级约束文件结构|AI项目级约束文件结构]] | 项目必须有能让 AI 恢复上下文的控制文件，入口文件不能写成泛泛原则。 |
| [[30_shared/architectures/AI-coding生命周期控制协议|AI coding 生命周期控制协议]] | 每个任务必须经历 `task_start -> task_plan -> task_implement -> task_verify -> task_close -> memory_file_back`。 |
| [[30_shared/architectures/AI模块测试验收证据协议|AI模块测试验收证据协议]] | 任务完成要按 L0-L8 提供证据，不能只说“已测试”。 |
| [[30_shared/architectures/资料摄入质量协议|资料摄入质量协议]] | 新资料进入项目或 Wiki 时，要保留来源、结构、引用和沉淀路由。 |

这意味着个人最小三句话：

```text
开始工作。
继续。
收工。
```

背后不是随意聊天，而是由上述协议驱动的项目状态机、控制文件更新、分层验收和 Wiki 回写。

## 1. 全局文件和项目文件的分工

你的全局文件已经有：

```text
C:\Users\jarvan_iv\.codex\AGENTS.md
C:\Users\jarvan_iv\.claude\CLAUDE.md
```

它们解决“所有项目都必须遵守的原则”，但不能解决某个具体项目的上下文。

真实项目必须再有项目级文件：

```text
<project>/CLAUDE.md
<project>/AGENTS.md
<project>/PRODUCT_SPEC.md
<project>/ARCHITECTURE.md
<project>/TASKS.md
<project>/TESTING.md
<project>/DEPLOYMENT.md
<project>/OPERATIONS.md
<project>/CHANGELOG.md
<project>/docs/design/
<project>/docs/adr/
<project>/docs/runbooks/
<project>/docs/growth/
```

分工：

| 文件 | 作用 | 谁主要读取 |
|---|---|---|
| `CLAUDE.md` | Claude Code/兼容工具入口 | Claude Code、其他兼容该约定的 AI 工具 |
| `AGENTS.md` | Codex 项目入口 | Codex |
| `PRODUCT_SPEC.md` | 产品目标、用户、范围、非目标 | 人和 AI |
| `ARCHITECTURE.md` | 架构边界、模块、数据流 | 人和 AI |
| `TASKS.md` | 当前任务池、状态、验收 | 人和 AI |
| `TESTING.md` | 验证命令和测试策略 | 人和 AI |
| `DEPLOYMENT.md` | 上线、环境、回滚 | 人和 AI |
| `OPERATIONS.md` | 日志、监控、故障处理 | 人和 AI |
| `CHANGELOG.md` | 版本级变更 | 人、用户、AI |

规则：

```text
全局文件只写通用原则。
项目文件写具体事实。
用户不需要背项目文件和读取顺序，只需要说“开始工作”“继续”“收工”。
AI 每次进入项目，必须自己恢复项目上下文、读取必要入口和控制文件。
如果 AI 输出和项目文件冲突，以项目文件为准。
```

日常使用分两层：

| 层级 | 用户怎么说 | AI 内部做什么 |
|---|---|---|
| 用户层 | `开始工作`、`继续`、`收工`、`这是一个需求变更：...` | 不暴露文件读取顺序 |
| Agent 层 | 自动读取项目入口、项目控制文件和项目 wiki | 执行边界、验证、回写 |

## 2. 新项目 0-1 启动流程

### Step 1：想法入库

你对 AI 说：

```text
我准备做一个新项目。先不要写代码。
请根据我的想法，帮我整理：
- 目标用户
- 真实痛点
- 使用场景
- MVP 必须做
- 当前版本明确不做
- 竞品和差异点
- 需要我确认的问题
输出为 PRODUCT_SPEC.md 初稿。
```

验收：

```text
3 句话能讲清楚用户、痛点、方案。
MVP 不超过 3 个核心功能。
非目标至少 5 条。
```

### Step 2：原型验证

你对 AI 说：

```text
基于 PRODUCT_SPEC.md，先做高保真可点击原型，不写生产代码。
输出：
- 核心用户路径
- 关键页面
- loading / empty / error 状态
- 移动端和桌面端布局
- 需要用户确认的体验问题
```

验收：

```text
核心路径能点通。
没有只靠视觉包装掩盖产品逻辑。
能发现至少 3 个交互或需求问题。
```

### Step 3：架构定边界

你对 AI 说：

```text
基于 PRODUCT_SPEC.md 和原型，先不要写业务代码。
请输出 ARCHITECTURE.md：
- 技术栈选择
- 模块边界
- 数据模型
- API contract
- 权限模型
- 外部依赖
- 哪些地方未来最容易变
- 哪些地方必须保持稳定
要求优先简单单体架构，不要过度工程。
```

验收：

```text
知道核心表有哪些。
知道核心 API 有哪些。
知道业务逻辑放在哪里。
知道哪些目录禁止乱改。
```

### Step 4：建立项目控制文件

你对 AI 说：

```text
请基于当前项目生成项目级控制文件：
- CLAUDE.md
- AGENTS.md
- TESTING.md
- DEPLOYMENT.md
- OPERATIONS.md
- TASKS.md
要求内容具体到本项目，不要写泛泛原则。
```

验收：

```text
AI 能根据文件知道怎么启动项目。
AI 能根据文件知道怎么测试。
AI 能根据文件知道哪些地方不能乱改。
AI 能根据文件知道完成任务要汇报什么。
```

### Step 5：脚手架和第一条主路径

你对 AI 说：

```text
只实现第一条主路径。
不要做完整系统。
先建立脚手架、基础页面、核心数据模型、最小 API 和一条 E2E。
完成后运行 TESTING.md 中定义的 verify 命令。
```

验收：

```text
本地能启动。
第一条用户路径能跑。
verify 能跑。
没有无关功能。
```

## 3. 每天的实际工作节奏

### 开工 10 分钟

只做三件事：

```text
1. 看 TASKS.md，选今天最多 3 个任务。
2. 每个任务写验收标准。
3. 判断风险等级：P3/P2/P1/P0。
```

风险等级：

| 等级 | 示例 | 处理方式 |
|---|---|---|
| P3 | 文案、样式、小 UI | AI 可直接改，人工快速看 |
| P2 | 普通功能 | AI 先分析，再实现，跑测试 |
| P1 | 登录、权限、核心流程 | 先设计、先测试、人类逐文件审 |
| P0 | 支付、数据删除、迁移、安全 | AI 只辅助分析和测试，谨慎实现 |

### 开发循环

每个任务固定 6 步：

```text
1. Analyze：AI 只分析影响面，不改代码。
2. Plan：AI 给最小实现方案和测试计划。
3. Test：先补测试或验收脚本。
4. Implement：AI 只改指定范围。
5. Verify：运行 TESTING.md 中的命令。
6. Review：AI review + 你审风险。
```

任务入口自然语言：

```text
继续。
```

Agent 内部必须先完成：恢复项目上下文、确认任务边界、评估风险、给出最小方案和验证方式；如果有高风险或需求不清，再问用户。

### 收工 10 分钟

更新：

```text
TASKS.md：任务状态、剩余问题
CHANGELOG.md：版本级变化才写
OPERATIONS.md：发现新的运维问题才写
项目 Wiki：重要决策和复盘才写
```

收工 prompt：

```text
收工。
```

Agent 内部必须根据今天的 diff 和验证结果更新 `TASKS.md`、必要的项目控制文件和 wiki 回写候选，不改无关文档。

## 4. 需求变更工作流

需求变更不能直接让 AI 改代码。

固定流程：

```text
1. 更新 PRODUCT_SPEC.md 的变更说明。
2. 让 AI 做影响面分析。
3. 更新或新增验收标准。
4. 判断是否影响 ARCHITECTURE.md。
5. 先改测试。
6. 只改受影响模块。
7. 跑局部测试和回归。
8. 更新 TASKS.md / CHANGELOG.md。
```

需求变更自然语言：

```text
这是一个需求变更：<写清变更>。
```

Agent 内部必须输出：变更类型、影响路径、受影响数据/API/页面、必须保持的旧行为、需要新增或修改的验证、最小修改范围、是否需要调整架构或任务记录。

验收：

```text
小变更只改小范围。
旧行为有回归测试。
变更原因写入 PRODUCT_SPEC.md 或 TASKS.md。
```

## 5. Bug 修复工作流

Bug 不要直接修。

固定流程：

```text
1. 复现。
2. 定位。
3. 写失败测试。
4. 最小修复。
5. 跑回归。
6. 沉淀防复发规则。
```

Bug prompt：

```text
请调查这个 bug，先不要修：
[bug 描述]

要求：
- 找到复现路径
- 找到可能根因
- 指出影响范围
- 先写一个能失败的测试或验收步骤
- 再提出最小修复方案
```

验收：

```text
没有复现不修。
没有根因不大改。
修复后测试能证明 bug 消失。
```

## 6. 发布工作流

发布前不要只看页面能不能打开。

发布清单：

```text
1. TASKS.md 中本版本任务已关闭。
2. TESTING.md 的 verify 命令通过。
3. 数据库 migration 已检查。
4. 环境变量已检查。
5. DEPLOYMENT.md 有发布命令。
6. OPERATIONS.md 有回滚方式。
7. CHANGELOG.md 已更新。
8. 核心用户路径手动走一遍。
```

发布 prompt：

```text
发布前帮我检查一遍。
```

Agent 内部必须输出：本次发布内容、已通过验证、未验证风险、数据库/环境变量影响、回滚步骤、发布后观察项。

验收：

```text
知道如何上线。
知道如何回滚。
知道出问题看哪里。
```

## 7. 运维和反馈工作流

用户反馈进入产品，不直接进入代码。

反馈处理：

```text
1. 记录原话。
2. 判断是 bug、需求、误解、销售线索还是使用障碍。
3. 对 bug 走 Bug 工作流。
4. 对需求走需求变更工作流。
5. 对误解更新文档或 onboarding。
6. 对销售线索更新 SALES.md。
```

反馈 prompt：

```text
请整理这批用户反馈：
[粘贴反馈]

分类为：
- bug
- 需求
- 使用障碍
- 文档问题
- 销售线索
- 暂不处理

每条给出建议动作和是否进入 TASKS.md。
```

## 8. 推广和销售工作流

每周固定一次增长循环，不要等产品完美。

每周输出：

```text
1 篇长内容或案例
3 条短内容
10 个目标用户触达
3 个用户访谈或反馈
1 次 landing page / onboarding 调整
```

AI 可做：

```text
竞品分析
用户画像
内容草稿
冷邮件
销售话术
FAQ
用户访谈问题
反馈分类
```

你必须审：

```text
是否真实
是否过度承诺
是否贴近目标用户
是否能带来反馈或转化
```

## 9. 判断流程是否有效

有效的信号：

```text
每个任务都有验收。
AI 每次能自动恢复项目上下文。
需求变更能局部修改。
bug 有复现和测试。
发布有回滚。
用户反馈能回流到 TASKS.md。
```

无效的信号：

```text
AI 每次都重新理解项目。
一个小需求改十几个文件。
没有 verify 命令。
上线靠肉眼试用。
文档很多但任务时不用。
Skill 很多但规则互相冲突。
```

## 10. 最小执行版本

如果嫌完整流程太重，至少执行这套：

```text
1. 每次开工只说：开始工作。
2. 推进任务只说：继续。
3. 结束一轮只说：收工。
4. 需求变更只说：这是一个需求变更：...
5. Bug 修复只说：修复这个 bug：...
6. 发布前只说：发布前帮我检查一遍。
```

这 6 条是用户层最小用法。文件读取、验证、回写和控制面维护都属于 agent 内部执行协议。
