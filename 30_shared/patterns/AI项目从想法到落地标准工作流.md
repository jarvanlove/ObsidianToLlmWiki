# AI项目从想法到落地标准工作流

## 0. 这份文档怎么用

这不是概念说明，而是操作手册。

你每次只需要做三件事：

1. 判断当前处于哪个阶段。
2. 复制对应阶段的提示词给 AI。
3. 用该阶段的验收标准判断能不能进入下一步。

如果你不知道当前在哪个阶段，先用下面这段提示词。

### 0.1 阶段定位提示词

```text
请先不要写代码，也不要直接写方案。
请根据当前项目资料和对话，判断我们处于哪个阶段：
0. 想法接收
1. 需求澄清
2. 方向研判
3. 老板汇报
4. PRD
5. 工程技术方案
6. 垂直切片开发计划
7. 开发执行
8. 测试验收
9. 发布交付
10. 反馈迭代

请输出：
1. 当前阶段
2. 为什么是这个阶段
3. 已有输入
4. 缺失输入
5. 下一步应该让我给你什么资料或确认什么问题
6. 当前不应该做什么
```

通过标准：

- AI 能说清楚当前阶段。
- AI 没有直接跳到写代码。
- AI 明确下一步要产出什么。

---

## 1. 总流程地图

完整流程如下：

```text
想法接收
  -> 需求澄清
  -> 方向研判
  -> 老板汇报
  -> 产品 PRD
  -> 工程技术方案
  -> 垂直切片开发计划
  -> Slice 开发
  -> 测试验收
  -> 发布/交付
  -> 反馈迭代
```

异常分支随时可能插入：

```text
需求变更
重大 Bug
安全/权限问题
数据问题
测试失败
发布失败
线上事故
文档失真
```

一个真实企业级项目，不是只走主路径。异常分支必须有标准流程。

## 2. 阶段 0：想法接收

### 何时使用

老板或自己只有一个模糊想法，例如：

- “能不能用 AI 做一个投研系统？”
- “我有几个文档，你看看能做什么。”
- “这个东西能不能商业化？”

### 你要给 AI 的材料

- 老板原话。
- 你自己的理解。
- 文件、截图、链接。
- 当前你不懂的地方。

### 直接复制的提示词

```text
我现在只有一个初始想法，先不要写代码，也不要写 PRD。
请你帮我做“想法接收”：

输入如下：
[粘贴老板原话、我的理解、已有资料列表]

请输出：
1. 原始需求复述
2. 已确认事实
3. 我的假设和你的推测
4. 目前不确定的问题
5. 这个想法可能对应的产品方向
6. 现在为什么不能直接开发
7. 下一轮应该问老板/问我哪些问题
```

### AI 必须输出

- 事实和猜测分开。
- 不确定问题清单。
- 可能方向，但不下最终结论。

### 你要检查

- AI 有没有误解老板原话。
- AI 有没有把不确定内容当成事实。
- AI 有没有急着给技术方案。

### 通过标准

- 你能确认“AI 理解的基本是对的”。
- 关键不确定项被列出来。

### 下一步

进入阶段 1：需求澄清。

---

## 3. 阶段 1：需求澄清

### 何时使用

你已经有一些资料，但仍然不知道老板真正想要什么，或者需求需要多轮沟通。

### 直接复制的提示词

```text
请进入需求澄清阶段，先不要写 PRD，也不要写技术方案。

背景：
[粘贴当前已知背景]

请帮我梳理：
1. 老板/用户真正想解决的问题
2. 目标用户是谁
3. 用户现在怎么解决这个问题
4. 可能的商业模式
5. 当前已有资源
6. 当前最大不确定性
7. 第一阶段最应该验证什么
8. 需要继续问老板的 10 个问题
9. 如果老板回答不同，后续方向会怎么变化
```

### AI 必须输出

- 用户和场景。
- 业务目标。
- 商业假设。
- 第一阶段验证目标。
- 问题清单。

### 你要检查

- 是否把“老板想法”翻译成“业务目标”。
- 是否区分 C 端、B 端、内部工具。
- 是否列出第一阶段验证对象。

### 通过标准

- 你能带着问题去找老板继续确认。
- 需求没有被直接写成开发任务。

### 下一步

如果老板还没确认，继续阶段 1。

如果方向大致清楚，进入阶段 2：方向研判。

---

## 4. 阶段 2：方向研判

### 何时使用

你需要给老板或自己判断：

- 这个想法到底该做什么。
- 哪个方向优先。
- 哪些方向不做。
- 能不能形成商业闭环。

### 直接复制的提示词

```text
请基于目前全部资料，输出一份方向研判报告。
注意：这是给决策者看的，不是技术文档。

要求：
1. 决策者不需要回看旧对话
2. 先讲一句话结论
3. 说明当前背景
4. 说明我们真正要解决什么问题
5. 给出推荐方向
6. 给出不推荐方向及原因
7. 说明产品形态
8. 说明商业模式
9. 说明第一阶段建议做什么
10. 说明主要风险
11. 列出还需要老板确认的问题
```

### AI 必须输出

- 老板能看懂的报告。
- 推荐方向。
- 不推荐方向。
- 风险。
- 下一步确认项。

### 你要检查

- 是否站在业务视角，而不是技术视角。
- 是否用老板听得懂的语言。
- 是否可以支撑老板拍板。

### 通过标准

- 老板或你自己能确认大方向。
- 能进入 PRD 阶段。

---

## 5. 阶段 3：老板汇报

### 何时使用

你要把方向研判发给老板，而不是只给自己看。

### 直接复制的提示词

```text
请把当前方向研判整理成一份给老板看的汇报文档。

要求：
1. 老板只看这一份就能明白，不需要回看旧版本
2. 语言要像汇报，不要像聊天记录
3. 先说结论，再说原因
4. 把老板关心的商业闭环、质量风险、下一步讲清楚
5. 如果有待确认问题，单独列出
6. 如果某些问题已经确认，不要再写成待确认
7. 输出 Markdown
```

### AI 必须输出

- 独立可读的老板汇报版。
- 已确认和待确认分开。
- 下一步行动明确。

### 你要检查

- 老板看了是否会懵。
- 是否还残留已过期的待确认问题。
- 是否过度技术化。

### 通过标准

- 老板认可或给出明确反馈。
- 老板反馈能转成 PRD 输入。

---

## 6. 阶段 4：产品 PRD

### 何时使用

老板已经认可方向，需要把它变成产品和开发基准。

### 直接复制的提示词

```text
请基于已确认方向，输出产品 PRD。
注意：PRD 是产品需求基准，不是代码开发计划。

请包含：
1. 产品一句话
2. 背景与输入资料
3. 目标用户和用户角色
4. 业务目标
5. 产品目标
6. MVP 范围
7. 明确不做什么
8. 核心业务流程
9. 功能模块
10. 页面需求
11. 数据模型草案
12. 权限和审核规则
13. 关键质量规则
14. 验收标准
15. 给后续 AI 开发助手的执行指令
```

### AI 必须输出

- 可作为产品基准的 PRD。
- MVP 和非目标。
- 验收标准。
- 数据模型草案。

### 你要检查

- 是否写得足够细，开发者能看懂。
- 是否没有把未来所有东西都塞进 MVP。
- 是否明确哪些不做。

### 通过标准

- 老板或产品负责人认可。
- 可以进入技术方案和垂直切片计划。

---

## 7. 阶段 5：工程技术方案

### 何时使用

PRD 已经确定，但还不能直接写代码。

### 直接复制的提示词

```text
请基于 PRD 输出工程技术方案，先不要写代码。

请包含：
1. 推荐技术栈
2. 系统形态
3. 模块边界
4. 数据流
5. 数据库核心实体
6. API 设计原则
7. 权限模型
8. 文件存储策略
9. 外部服务和数据源
10. AI 工作流接入方式
11. 测试策略
12. 部署和运维初步方案
13. 重大技术决策和理由
14. 当前不引入的技术
```

### AI 必须输出

- 技术架构。
- 模块边界。
- 数据模型和 API 方向。
- 测试与部署策略。

### 你要检查

- 是否过度工程。
- 是否引入你不会用或不想用的技术。
- 是否能支撑 PRD。

### 通过标准

- 可以更新 `ARCHITECTURE.md`。
- 可以进入垂直切片计划。

---

## 8. 阶段 6：垂直切片开发计划

### 何时使用

PRD 和技术方向已明确，需要拆成可执行开发阶段。

### 直接复制的提示词

```text
请基于 PRD 和技术方案，按垂直切片拆开发计划。

要求：
1. 不要按“先后端、再前端”的横向方式拆
2. 每个 Slice 必须端到端可演示
3. 每个 Slice 包含数据模型、API、UI、验收、文档更新
4. 先做内部主路径，再做 AI，再做商业化增强
5. 标明当前阶段、下一阶段、未来迭代阶段
6. 标明每个 Slice 不做什么

每个 Slice 请按以下结构：
- 业务目标
- 用户路径
- 数据模型
- API
- UI
- AI/自动化
- 验收
- 文档更新
- 不做范围
```

### AI 必须输出

- Slice 列表。
- 每个 Slice 的端到端范围。
- 阶段划分。
- 每个 Slice 的不做范围。

### 你要检查

- 每个 Slice 是否能演示。
- 是否过早引入复杂功能。
- 是否覆盖当前 MVP 和第一轮业务闭环。

### 通过标准

- 你可以清楚知道从 Slice 0 到后续阶段的顺序。
- 仍然不代表马上开发，开发时间由你决定。

---

## 9. 阶段 7：开发执行

### 何时使用

你明确告诉 AI：开始开发某个 Slice。

如果你没有说开始开发，AI 不应默认写代码。

### 直接复制的提示词

```text
开始开发 Slice X。

请先读取：
1. AGENTS.md / CLAUDE.md
2. PRODUCT_SPEC.md
3. ARCHITECTURE.md
4. TESTING.md
5. TASKS.md
6. 对应 Slice 开发计划

要求：
1. 只实现 Slice X，不做额外功能
2. 先说明计划和预计修改文件
3. 再实施
4. 完成后运行 TESTING.md 中最小相关验证
5. 更新 TASKS.md 和必要文档
```

### AI 必须输出

- 实施计划。
- 修改文件。
- 验证结果。
- 风险和未完成项。

### 你要检查

- 是否越界做了其它 Slice。
- 是否跑了验证。
- 是否更新文档。

### 通过标准

- 本 Slice 可运行、可演示、可验证。

---

## 10. 阶段 8：测试验收

### 何时使用

某个 Slice 完成，或者一个版本准备交付。

### 直接复制的提示词

```text
请对当前版本做测试验收，先不要改代码。

请输出：
1. 当前应测试的核心路径
2. 自动化测试命令
3. 手工验收清单
4. 权限和安全检查点
5. 数据一致性检查点
6. 已通过项
7. 失败项
8. 阻塞项
9. 是否可以进入下一阶段
```

### AI 必须输出

- 测试清单。
- 测试结果。
- 阻塞风险。
- 是否可进入下一阶段。

### 你要检查

- 是否只测了 happy path。
- 是否覆盖错误输入、权限、空状态。
- 是否记录未验证风险。

### 通过标准

- 核心路径通过。
- 阻塞问题已处理或明确延期。

---

## 11. 阶段 9：发布/交付

### 何时使用

准备上线系统、交付文档、交付报告或给老板/客户演示。

### 直接复制的提示词

```text
请做发布/交付前检查。

请检查：
1. 本次交付内容
2. 已完成任务
3. 未完成但不阻塞的事项
4. 测试结果
5. 数据库/环境变量/部署影响
6. 回滚方案
7. 文档是否同步
8. 给老板/客户看的说明
9. 发布后观察项
10. 是否建议交付
```

### AI 必须输出

- 发布/交付检查报告。
- 风险。
- 回滚或补救方案。

### 你要检查

- 是否知道出问题怎么回退。
- 是否还有未同步文档。
- 是否有不该对外暴露的内容。

---

## 12. 阶段 10：反馈迭代

### 何时使用

老板、用户、测试人员或你自己提出反馈。

### 直接复制的提示词

```text
请整理这批反馈，先不要改代码。

反馈如下：
[粘贴反馈]

请分类为：
1. 需求变更
2. Bug
3. 体验问题
4. 数据问题
5. 权限/安全问题
6. 文档问题
7. 商业线索
8. 暂不处理

每条请给出：
- 分类
- 严重程度
- 影响范围
- 建议动作
- 是否进入 TASKS.md
- 是否需要更新 PRD/ARCHITECTURE/TESTING
```

### 通过标准

- 反馈没有直接变成代码修改。
- 每条反馈有处理路径。

---

## 13. 异常分支 A：需求变更

### 何时使用

老板改口、用户提出新需求、范围扩大、商业模式变化。

### 直接复制的提示词

```text
这是一个需求变更，先不要改代码。

变更内容：
[粘贴变更]

请输出：
1. 这是小变更、中变更还是重大变更
2. 影响哪些用户流程
3. 影响哪些页面
4. 影响哪些数据模型
5. 影响哪些 API
6. 影响哪些测试
7. 是否影响 PRD
8. 是否影响 ARCHITECTURE
9. 是否影响当前 Slice 计划
10. 最小处理方案
11. 不建议现在做的部分
```

### 处理规则

- 小变更：更新 `TASKS.md`，局部实现。
- 中变更：先更新 PRD 和 Slice 计划。
- 重大变更：回到方向研判或 PRD 阶段。

### 通过标准

- 影响面清楚。
- 旧功能是否受影响说清楚。
- 不直接冲进代码。

---

## 14. 异常分支 B：重大 Bug

### 何时使用

功能不可用、数据错误、权限绕过、报告生成错误、线上事故。

### 直接复制的提示词

```text
这是一个重大 Bug，请先调查，不要直接修。

Bug 描述：
[粘贴现象]

请输出：
1. 复现路径
2. 影响范围
3. 严重程度
4. 可能根因
5. 需要查看哪些文件/日志/数据
6. 临时止血方案
7. 最小修复方案
8. 回归测试清单
9. 是否需要复盘和文档更新
```

### 处理规则

```text
复现 -> 定级 -> 止血 -> 根因 -> 修复 -> 回归 -> 复盘
```

### 通过标准

- 没有复现不大改。
- 没有根因不重构。
- 修复后必须有回归测试。

---

## 15. 异常分支 C：安全和权限

### 何时使用

涉及登录、角色、数据权限、API Key、敏感资料、付费内容、企业客户数据。

### 直接复制的提示词

```text
这是安全/权限相关问题，请先做安全影响分析，不要直接实现。

问题描述：
[粘贴问题]

请输出：
1. 涉及哪些角色
2. 涉及哪些数据
3. 涉及哪些 API
4. 是否有越权风险
5. 是否有数据泄露风险
6. 是否涉及 API Key 或密钥
7. 需要哪些权限规则
8. 需要哪些审计日志
9. 测试用例
10. 是否需要更新 SECURITY.md / ARCHITECTURE.md
```

### 必须检查

- 未登录访问。
- 普通用户访问管理员数据。
- A 客户访问 B 客户数据。
- 未审稿报告被发布。
- API Key 泄露。
- 敏感资料被导出。

### 通过标准

- 权限边界写清楚。
- 有反向测试。
- 安全文档更新。

---

## 16. 异常分支 D：测试失败

### 何时使用

测试、构建、类型检查、手工验收失败。

### 直接复制的提示词

```text
测试失败了，请先分析失败原因，不要直接乱改。

失败输出：
[粘贴日志]

请输出：
1. 失败命令
2. 失败类型
3. 可能根因
4. 影响范围
5. 最小修复方案
6. 需要补充的测试
7. 修复后应重新运行哪些命令
```

### 通过标准

- 知道失败原因。
- 修复后重新运行失败命令。
- 不用跳过测试掩盖问题。

## 17. 异常分支 E：数据库和数据修复

### 何时使用

涉及表结构、数据迁移、数据修复、指标口径、生产数据。

### 直接复制的提示词

```text
这是数据库/数据变更，请先做数据影响分析，不要直接改。

变更内容：
[粘贴内容]

请输出：
1. 涉及哪些表
2. 涉及哪些字段
3. 是否需要 migration
4. 是否需要数据回填
5. 是否需要备份
6. 回滚方案
7. 对历史数据的影响
8. 测试数据准备
9. 验证 SQL 或检查步骤
10. 是否需要更新 ARCHITECTURE/TESTING/OPERATIONS
```

### 通过标准

- 有回滚方案。
- 有数据校验。
- 不直接改生产数据。

## 19. 新手最小用法

如果你不想记复杂流程，只记下面 8 句：

```text
1. 我有一个新想法，先不要写代码，请帮我做想法接收。
2. 请进入需求澄清阶段，帮我列出需要问老板的问题。
3. 请基于当前资料输出给老板看的方向研判报告。
4. 请基于已确认方向输出 PRD。
5. 请基于 PRD 输出工程技术方案。
6. 请基于 PRD 和技术方案按垂直切片拆开发计划。
7. 开始开发 Slice X，只做这个 Slice，并运行验证。
8. 收工，请更新项目控制文件和 Wiki。
```

遇到异常，只记下面 5 句：

```text
1. 这是一个需求变更，先做影响面分析。
2. 这是一个重大 Bug，先复现和定位，不要直接修。
3. 这是安全/权限问题，先做安全影响分析。
4. 测试失败了，先分析失败原因。
5. 这是数据库/数据变更，先做数据影响分析和回滚方案。
```

## 20. 判断流程是否健康

健康信号：

- 每个阶段都有明确产物。
- 每个产物都有验收标准。
- AI 不会在需求不清时直接写代码。
- 每个 Slice 都能演示。
- 需求变更先分析影响面。
- Bug 先复现再修。
- 权限、安全、数据变更有专门流程。
- 项目控制文件持续更新。
- Wiki 只沉淀长期结论。

危险信号：

- 老板一句话后直接开写代码。
- PRD 没被确认就拆开发。
- 只有后端完成，前端不可用。
- AI 引入你不会维护的技术。
- 测试失败但跳过。
- 文档路径移动后引用没同步。
- 已确认事项还写成待确认。
- 所有东西都塞进 MVP。
