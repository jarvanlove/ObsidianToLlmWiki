# AI产品UI设计交付工作流

## 用户只需怎么说

```text
开始工作：重新设计订单详情页。
```

Agent 读取项目控制面，判定 UI 等级并说明需要的最小验证。U0/U1 可以直接推进；U2/U3 先停在方向阶段，不写生产页面。

当你希望使用某个已有能力时，表达目的和边界：

```text
用 Stitch 探索三个视觉方向，不改生产代码。
```

```text
以这个 Figma 节点为已批准参考，实现设置页。
```

```text
用 <UI Skill 名称> 只做当前页面的视觉 QA，不改代码。
```

不要只说“用某个 Skill 美化页面”。这没有产品任务、约束和验收口径。Agent 应把它转为 U1 的问题诊断，或 U2 的视觉方向任务，而不是直接重写页面。

当项目没有任何参考图时，也不需要让用户先学习色号。Agent 使用固定回退视觉方向，或根据用户表达的“高端、清爽、文化感、活动页”等气质，从受控方向中提出少量候选。项目一旦已有 `UI_VISUAL_BASELINE.json`，Agent 必须沿用它；普通页面不得借机换主题。

## U1：局部 UI 修改

适用：已批准组件内的样式修正、交互 Bug、状态缺失、响应式问题。

```text
开始工作：修复移动端筛选栏遮挡提交按钮。
```

Agent 必须：读取 UI Contract、复用当前 Token/组件、覆盖受影响状态、提供浏览器截图和 QA 证据。它不得借机替换页面布局、字体、组件库或品牌色。

## U2：新页面或流程重做

适用：新用户流程、核心页面重构、信息层级或视觉重心改变。

```text
开始工作：为专业用户重做安全设置流程。
```

流程：

1. Agent 创建 UI task，梳理用户、主任务、真实内容、状态矩阵和视口。
2. 视觉方向能力生成至少两个有差异的候选，说明构图、密度、排版、色彩与反例。
3. 用户以自然语言批准一个方向，例如“第二个方向批准，继续”。
4. Agent 把批准方向转为项目组件、Token、模式和验证计划。
5. 实现后，由独立 Visual QA 检查截图与批准基准。
6. `收工` 前记录证据并关闭 UI task。

用户只作一次不可替代的审美决定，不需要背模板或脚本名。

## U3：设计系统改变

适用：主题、字体、主色、圆角、组件库、跨产品模式或 Golden Flow 信息架构变化。

除 U2 流程外，必须生成 Design RFC，说明问题、替代方案、Token/组件影响、迁移、无障碍、性能与回滚。没有批准 RFC，AI 只能分析和产出候选，不能批量改页面。

## 收工

```text
收工。
```

Agent 对 UI task 自动检查：

- U2/U3 是否保存了批准方向。
- 截图是否覆盖约定视口和关键状态。
- Visual QA 是否独立于实现者。
- 无障碍证据是否存在。
- 是否出现新 Token、组件、依赖或基准图，需要 RFC/文档更新。

缺任何硬证据时，任务保持进行中并说明阻塞原因；不能以“页面看起来可以”关闭。
