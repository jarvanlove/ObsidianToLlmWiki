两种工作流，一个执行内核

个人工作流解决一个人如何稳定完成任务。团队工作流把多个个人任务组织成分支、角色、集成和验收体系。

一个人驱动 AI 做 0 到 1 项目

每一步都必须有文件承载、AI 输入、验收条件和下一步出口。

01
想法入库把模糊想法拆成目标用户、痛点、MVP 和非目标。
02
规格与架构用 PRODUCT_SPEC 和 ARCHITECTURE 固定产品和技术边界。
03
垂直切片每个 Slice 端到端覆盖数据、API、页面和验收。
04
验证收工用证据关闭任务，再更新 TASKS、TESTING 和 Wiki 候选。

多人弱编码团队的协作控制面

每个人只关心自己的任务文档，AI 读取公共规则，组长逐个集成。

01
负责人定边界确定 main、dev、team 分支、验收标准和禁止事项。
02
组长拆任务按官网组、后台组分配模块，避免多人直接改同一片公共区域。
03
组员走个人闭环个人分支实现、验证、提交，只更新自己负责的任务状态。
04
组长逐个集成一个人一合、一验、一记录，冲突时停止并说明语义。

团队工作流不是替代个人工作流

它是在个人任务闭环外增加角色、分支、冲突、集成、验收和记忆控制层。

个人文档 组长集成 公共文档治理 共享 server 边界 Git 保护

AI 执行生命周期

任务不能从“写代码”开始，也不能用“写完了”结束。生命周期让 AI 工作可追踪。

task_start确认任务、身份、分支、风险和上下文。
task_plan输出最小计划、预计文件和验证方式。
task_implement按边界实现，不做无关扩展。
task_verify运行最小但充分的验证。
task_close更新任务、索引、风险和提交记录。
memory_file_back只把长期有效结论写入 Wiki。

验收证据 L0 到 L8

涉及哪一层，就验证哪一层。页面能打开不是完成，代码写完也不是完成。

L0格式、类型、lint、构建。
L1纯函数、schema、状态转换。
L2API、服务、错误码和认证。
L3真实数据库、migration、seed。
L4浏览器操作到 API 再到数据。
L5控制台、响应式、交互状态。
L6未登录、无权限、密钥和敏感数据。
L7来源、口径、置信度和人工确认。
L8控制文件、索引和 Wiki 回写。

团队角色协作边界

角色边界越清晰，AI 越不容易越界。每个角色只承担自己应该承担的责任。

项目负责人

  • 定目标和边界
  • 最终验收
  • 决定是否合入 main
  • 沉淀共享经验

组长

  • 拆组内任务
  • 收个人分支
  • 处理冲突
  • 更新组进度

组员

  • 读取个人文档
  • 只做个人任务
  • 运行验证
  • 提交个人分支

AI

  • 读取规则
  • 执行生命周期
  • 提供验收证据
  • 更新必要文档
