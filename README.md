# ObsidianToWiki

让 AI 在每次写代码前读懂项目、在写完后留下可验证的记忆，而不是只交付一堆没人敢维护的代码。

ObsidianToWiki 是一个本地优先的 AI 项目记忆与工程控制系统。它把私人 Obsidian Wiki、项目控制文件、Git 事实和 AI 编码流程连接起来，让知识不会随着对话结束而丢失，也让 AI 的每次修改都有范围、证据和责任边界。

本项目参考了 Andrej Karpathy 提出的 [Karpathy LLM-Wiki 方法论](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)：保留原始材料，用 Markdown、索引和可追溯链接维护长期知识，再让 LLM 负责持续整理、检索和更新。ObsidianToWiki 在此基础上增加了项目接入、工程门禁、风险分级、上下文收据、记忆编译和安全更新。

给项目接入一次后，系统会在修改前先找根因和影响范围，在验证后自动记录可追溯的长期结论。用户可以直接描述需求；`开始工作` 只是可选的检查与恢复口令。

## 它解决什么问题

普通 AI 编码常见三个问题：

- 每次对话都像重新认识项目，历史决策、风险和约束容易丢失。
- AI 只追求“跑起来”，开发者不知道它改了什么、为什么改、是否越界。
- 文档越积越多，最后人不想看，模型也不适合一次性全读。

ObsidianToWiki 把流程改成：

```text
用户用自然语言提出需求
        ↓
AI 读取当前代码、项目控制文件和有界 Wiki 上下文
        ↓
按风险确定范围、计划、审批和验证要求
        ↓
实施并用测试、Git diff、截图或运行结果证明
        ↓
只把可复用、可追溯的结论写回私人 Wiki
```

代码仍以 Git 为准，私人 Wiki 负责长期记忆，AI 推理不能冒充项目事实。

## 使用者需要做什么

首次安装一次、给项目接入一次，之后正常说话即可：

```text
帮我修复登录超时问题
继续
项目现在怎么样
收工
```

文件读取、上下文检查、任务计划、验证、收据和 Wiki 回写由 Agent 负责。`开始工作`、`继续`、`收工` 是检查和恢复口令，不是每天必须执行的仪式。

`项目现在怎么样` 直接返回文字状态，不生成 HTML 页面或另一套项目数据。

## 当前具备的能力

### 1. 私人 Wiki 与项目长期记忆

- 在本地创建和维护私人 Obsidian Vault。
- 通过 `wiki.context.json`、`AGENTS.md` 和 `CLAUDE.md` 将代码项目接入 Wiki。
- 维护项目概览、架构、决策、任务、来源、风险、时间线和长期记忆。
- 将个人知识、项目知识、共享方法和交付物分层保存。

### 2. 材料摄取、检索和回写

- 摄取 Markdown、文本、代码、PDF、DOCX、PPTX 等材料。
- 长文档拆成来源说明、文档地图和章节笔记，并保留出处。
- 使用本地 SQLite FTS5 索引检索；索引是可删除重建的缓存，不是知识源。
- 将有价值的回答写回 Wiki，避免结论困在聊天记录里。

### 3. 人类可控的 AI 工程流程

- 任务经过开始、计划、实施、验证、关闭和记忆回写。
- 当前代码与运行结果优先于项目文档，项目文档优先于可信记忆，AI 猜测永远不能成为事实。
- P3 到 P0 风险分级；风险越高，需要的人类确认和独立证据越强。
- 用 Context Receipt 记录本次任务真正读取了什么、缺少什么、哪些内容不可信。
- 只将有证据的稳定结论编译为长期记忆，旧历史退出默认上下文但不会被删除。
- 通过“人类理解门禁”和能力恢复机会，让开发者重新掌握代码、影响范围和风险，而不是完全依赖 AI 自产自销。

### 4. UI 设计治理

- 按 U0-U3 判断 UI 影响范围。
- 内置 19 组可追溯配色方向，其中 6 组作为无参考设计图时的可靠默认值。
- 用户不满意时，AI 自动判断是局部问题还是整体方向问题，并给出 3 个容易理解的选择。
- 重要 UI 变更需要方向确认、浏览器截图、Visual QA 和可访问性证据。
- Figma、Stitch 和 UI Skills 可以执行设计工作，但不能覆盖项目已经批准的设计事实。

### 5. 安全安装和更新

- 公共运行时、私人 Wiki、全局 Skill 和项目桥接分别管理版本。
- 公共仓库更新只允许干净工作区和 fast-forward，不自动 stash、reset 或强制覆盖。
- 私人文件有修改时保留原文件，并生成候选文件和备份供人工处理。
- `wiki.private.json` 可排除不允许 ObsidianToWiki 索引或摄取的路径。
- Windows、macOS 和 Linux 使用同一套核心流程。

## 安装

### Windows

```powershell
git clone https://github.com/jarvanlove/ObsidianToLlmWiki.git
cd ObsidianToWiki
.\install.ps1
```

### macOS / Linux

```bash
git clone https://github.com/jarvanlove/ObsidianToLlmWiki.git
cd ObsidianToWiki
./install.sh
```

安装程序会创建隔离的 Python 环境、初始化或发现私人 Wiki、安装 Manager Skill、迁移状态并执行检查。私人 Wiki 默认保存在本机，不会自动上传到公共仓库。

## 给项目接入 Wiki

在需要接入的项目中告诉 AI：

```text
把当前项目接入我的私人 Wiki
```

系统会生成项目入口和本地上下文。真实本地路径只写入 Git 忽略的配置；可提交的模板不得包含用户机器的绝对路径。

接入后，开发者继续描述真实需求即可。AI 应先读取项目自己的 `AGENTS.md` 和相关控制文件，再决定范围、风险和验证方法。

## 数据放在哪里

```text
公共 ObsidianToWiki 仓库
├─ 可复用脚本、模板、协议和共享方法
└─ 不保存用户的真实项目知识

用户的私人 Wiki
├─ 个人知识
├─ 项目长期记忆
├─ 经审核的共享方法
└─ 输出与升级候选

接入的代码项目
├─ Git 管理的代码与项目控制文件
└─ .obsidiantowiki/ 本地任务状态和收据（默认不提交）
```

`.obsidiantowiki/` 是任务执行时的本地状态，不是项目知识库，也不是给用户浏览的页面。它可以包含本机路径，因此默认必须被 Git 忽略。长期结论应进入私人 Wiki，代码事实应进入 Git。

## 边界

- 这是本地工具和工程方法，不是托管知识平台。
- 它不能替代开发者理解代码，也不会保证 AI 自动生成正确产品。
- Wiki 损坏或缺少事实时，系统应明确降级或停止，不能用模型幻觉补齐。
- `wiki.private.json` 只约束 ObsidianToWiki 自己；若 AI 工具有更大的文件系统权限，仍需在对应工具中限制工作区和权限。
- 高风险任务必须由具体的人确认影响和剩余风险，AI 不能替人批准自己的工作。
